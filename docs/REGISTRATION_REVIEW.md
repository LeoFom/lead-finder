# Гостьовий режим та оцінка реєстрації

## Доступність при збої PostgreSQL

Поточний NestJS зберігає користувачів, парольні хеші, ліміти спроб входу та сесії у PostgreSQL. Без БД парольний вхід і перевірка серверної сесії недоступні, навіть коли процес Render працює. Гостьовий простір і захищена локальна база доступні незалежно. Копію парольних хешів на браузері для обходу входу не створюємо.

## Реалізований гість

Початковий режим — гостьовий, без запитів до API та форми входу. Бізнеси, профілі, CRM, локальна історія, пошук у наявній базі та CSV працюють у браузері. На першому відкритті база порожня. Дані зберігаються під окремим ключем guest-v1, з версією та ревізією. Зашифрована локальна база і серверна CRM мають окремі сховища.

Кнопка «Увійти» відкриває добровільний вхід існуючого власника. Гостьові записи не переносяться до акаунта автоматично. Вихід повертає гостьовий простір із його попередніми записами. Якщо NestJS або PostgreSQL недоступні, Next.js прибирає cookie з цього браузера, а серверна сесія в БД доживає до відкликання або строку дії. Гостьовий режим не отримує доступу до серверних даних.

Без дозволеного localStorage гість працює у пам’яті вкладки з попередженням. За переповнення сховища зміна відхиляється зі збереженням попереднього стану. Конфлікт іншої вкладки потребує перезавантаження. У браузері без Web Locks записи тимчасові, щоб паралельні вкладки не перезаписували дані.

Гостьові дані збережені без пароля в поточному профілі браузера. На спільному комп’ютері ними можуть користуватися наступні відвідувачі цього профілю. Для приватної роботи є окрема зашифрована база. Очищення даних сайту видаляє гостьові записи, тому важливі списки слід вивантажувати у CSV. Гість не має міжпристроєвої синхронізації або відновлення через email.

## Чому публічна реєстрація потребує окремого етапу

Зараз сервер обслуговує одного власника. Частина запитів до businesses, search_profiles, history та exports глобальна. Додавання ще одного User без ізоляції цих запитів призведе до ризику доступу до чужої CRM. Потрібні workspace/tenant ID у пов’язаних записах, унікальні ключі в межах tenant, міграція даних власника та серверна авторизація кожної операції за tenant. Для A/B-акаунтів тестувати прямий UUID-доступ, зміни, CSV, offline snapshot, історію і фонові завдання. [OWASP Multi-Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)

Після ізоляції можна додати signup, підтвердження пошти та запрошення. Публічну реєстрацію варто захистити квотами, лімітами створення акаунтів і повідомлень, щоб автоматичні запити не вичерпували безкоштовні ресурси. Перенесення гостьових даних у акаунт має бути явною окремою дією з попереднім переглядом, перевіркою походження, стабільним ключем повтору і захистом від перезапису CRM.

## Відновлення пароля

Для поточної NestJS-авторизації потрібні короткоживучий випадковий reset-token, його хеш у БД, одноразове атомарне використання, однакові відповіді для відомої й невідомої пошти, ліміти IP/email, дозволений базовий URL листа та відкликання сесій після зміни пароля. Пароль, токен і посилання відновлення не потрапляють у логи. БД потрібна і для перевірки токена. [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

Варіант збереження нинішньої авторизації — поштовий провайдер на кшталт Resend. На дату оцінки 19.11.2026 Free має ліміт 100 листів на день. Для довільних отримувачів потрібен власний підтверджений домен і налаштовані DNS-записи. Доставлення у вхідні, відсутність затримок і необмежені безкоштовні обсяги не гарантуються. Може знадобитися оплата домену або більший тариф при зростанні. [Тарифи](https://resend.com/pricing) · [Верифікація домену](https://resend.com/docs/dashboard/domains/introduction)

Альтернатива для окремого рішення — Managed Better Auth на Neon, де є підтвердження пошти й reset flow. Це вимагатиме перенесення поточного входу та зв’язку ідентичностей з CRM, а production-рекомендації Neon передбачають власний SMTP. Спільний SMTP придатний для початкової розробки. Ізоляцію даних різних користувачів все одно реалізує застосунок. Зміна auth provider не робить CRM доступною при відсутній БД. [Neon Auth production checklist](https://neon.com/docs/auth/production-checklist)

## Рішення, яке пропонується власнику

Поточний етап публікує гостьовий режим і залишає робочий вхід власника. Наступний окремий етап можна присвятити ізоляції акаунтів, реєстрації, підтвердженню пошти та відновленню пароля зі збереженням NestJS auth. Перед ним потрібно погодити поштовий сервіс і домен або окремо погодити міграцію до керованої авторизації. Публічна реєстрація і поштові розсилки у цьому етапі не вмикаються.

## Перевірки гостьового режиму

Unit-тести перевіряють порожній початковий стан, збереження записів, недоторканність ключа зашифрованої бази, конфлікт двох вкладок, переповнення та пошкодження сховища. Набір `pnpm test` містить 18 перевірок разом із наявними тестами прав та історії.

У headless Chrome на production-збірці перевірено: нуль API-запитів при гостьовому старті, ручне додавання, правку CRM, збереження після reload, CSV, помилку добровільного входу при API 503, повернення до гостя, повний offline reload і локальний пошук. Синтетичні API-fixtures підтверджують, що вхід та вихід не переносять приватні записи до гостьового сховища. Окремо перевірено роботу в пам’яті при заблокованому Storage та видалення cookie через BFF без конфігурації API. Реальну production-БД для цих перевірок не зупиняли.
