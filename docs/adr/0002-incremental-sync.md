# ADR 0002 · Повторний пошук та історія філії

**Статус** Прийнято як проєктне рішення у фазі 0. Схема й алгоритм належать до фаз 2, 5 та 7.

**Ідентичність.** Стабільний UUID представляє філію. Для збігу спочатку перевіряємо пару source_type + external_id. Домен чи телефон разом із сильно схожими назвою та фізичною адресою можуть дати однозначний збіг. Нечіткі збіги потрапляють на розгляд. Спільний домен мережі не зливає філії. Злиття зберігає відповідність старих ID, версії фактів і журнал для undo.

**Атомарність.** Під час створення run унікальний idempotency_key та lock на активний scope захищають від подвійного кліку. Нормалізований profile_hash включає місто, запит, синоніми, категоризацію, межі та їх версії. Кожна порція має стійкий checkpoint. Під транзакційним блокуванням бізнесу записати дозволену версію факту, компактний diff, membership, спостереження та checkpoint. Після commit повтор job розпізнає вже застосовану порцію. Для спостереження унікальна трійка run_id, source_type, business_id. Незалежний облік відсутності дедуплікується також за snapshot і scope.

**Історія.** Зміна дозволеного значення додає версію й посилання на попередню. Поточна проєкція та last_changed_at оновлюються при змістовній зміні. Оригінальний first_seen_at залишається датою першої появи. Відрізняємо час виконання job від дати підтвердження в джерелі. Для запізнілого релізу можна додати історичний доказ без відкату поточного стану. Старі дозволені значення доступні станом на run. Ліцензійне відкликання та правомірне видалення обробляються за ADR 0001.

**Ручні зміни.** Імпорт має доступ лише до свого набору полів. crm_entries, ручні перевірки та opt-out мають власні команди й аудит. Коли current-факт має ручне походження або lock, новий імпорт створює пропозицію з доказом. Ручна правка та імпорт серіалізуються одним блокуванням філії, після нього повторно читається lock. У результуючій проєкції ручне значення зберігає пріоритет при будь-якому порядку commit.

**Відсутність.** Після завершення конкретного джерела порівнюємо лише повні скани того самого профілю, джерела, меж і правил категоризації з новішим незалежним snapshot. За завершенням джерела стоїть транзакційна фіналізація під lock цього scope. Кандидати на missing — лише філії, раніше помічені цим джерелом у цьому профілі. Для ручної філії без такого зв’язку діє unchecked. Одна відсутність дає missing_once, друга послідовна дає missing_multiple. Повтор старого snapshot, partial, failed, skipped та скасований неповний скан не додають відсутності. Повернення додає подію reappeared, скидає лічильник і підтверджує seen. Інше джерело має власний облік. Для permanently_closed потрібне явне датоване свідчення. Суперечливий доказ іде на ручний розгляд.

## Контрольний приклад для фази 7

| Скан | Вхід | Очікуваний результат |
| --- | --- | --- |
| A, повний | A/B/C, B має b.example, користувач додав C нотатку | Три філії, три first_seen, незалежна CRM-нотатка |
| B, новіший повний | A/B/D, B має new-b.example | D створено один раз, B має обидві версії, C missing_once лише у джерелі |
| Повтор B або неповний запуск | Той самий B або обірваний batch | Жодного нового missing чи дубля, попередні філії доступні |
| C, новіший повний | A/B/C/D | C має SOURCE_REAPPEARED та стару нотатку, D зберігає UUID |
| Окремий варіант із lock | Власник вручну змінив сайт B під час імпорту | Власний сайт поточний, пропозиція із джерела та обидва докази доступні |

Повторний експорт конкретного run читає версіонований зріз і фільтри цього запуску. Після відкликання прав повторна генерація відкидає обмежені поля та фіксує причину. Додаткові сценарії включають різні філії бренду, паралельний retry, помилковий сайт і відновлення з копії. [Сценарії AC-03–AC-11, AC-19–AC-22](../../LEAD_FINDER_TECHNICAL_SPEC_UA.md)
